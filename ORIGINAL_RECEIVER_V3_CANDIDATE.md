# Original receiver v3 held contract candidate

`src/original-receiver-v3-contract.mjs` is a separate, pure offline successor candidate. It does not change the existing Original envelope2, database schema3/4, claim guards, or sender. An envelope3 here uses an Original specification and call plan at version3, so every selected binding, plan, task specification, and envelope hash is new. It cannot be replayed as envelope2. The module only returns `runtimeAdmission: HOLD` and a claim-witness2 **candidate**; no durable claim is inserted.

The selected plan slot commits the call and model; recipient identity, build and generation; physical sender principal; credential owner, ID and immutable generation hash; exact POST URL, method, ten ordered non-authentication headers and their hash; exact raw UTF-8 SDK body, byte length and hash; and receiver profile plus normalized UTF-8 body, byte length and hash. The receiver profile binds recipient identity/generation, ingress schema, normalizer and runtime hashes, endpoint and body policy. The full plan hash is in the signed Original specification, and that specification's hash is in the envelope. The comparison2 and held witness2 carry the wire, receiver, credential and sender commitments through distinct versioned hashes.

`createOriginalReceiverV3HeldContract` takes host-installed `verifyOriginal` and `observeHeldProjection` callbacks. Its public `compareHeld` method takes only an unforgeable authenticated capability; the observer receives a selector without the expected body or profile. The observation must match the signed envelope's full wire, authenticated sender principal, credential identity/generation, receiver profile and normalized body, and must report `HELD_BEFORE_POST`. The test fixture now commits the independent 307-byte PR35 Python-normalized body (SHA-256 `ab288a143d34de92156f01d0d4c4f5d05bbdc51eda4a335e16c8816205cd08b7`), preserving Python's `temperature:1.0` instead of reserializing it in JavaScript as `1`. The tests provide a synthetic verifier and synthetic held observation. A caller-supplied observation never enters the API. Configuring a callback that merely echoes user input would defeat the trust model and is outside this candidate.

Remaining qualifications are a real Original issuer and key registry, complete Flow graph and typed slot authority, authenticated sender/credential generation, authenticated receiver normalization from a pinned running deployment, and a fresh schema5 journal with admission and crash-safe physical-attempt semantics. The current CommunityAI callback exposes normalized data without an authenticated raw-wire/Original-proof carrier. The opt-in CommunityAI receiver v2 candidate captures post-ingress ASGI values; it is not this contract's authenticated pre-POST sender observation, so a separate post-POST receipt and explicit join remain necessary. This candidate does not establish that connection, prove a running deployment emitted its committed normalized bytes, or authorize a provider send. The separate `factory-original-v3-receiver` prototype uses the same proposed envelope/comparison/witness version numbers with a different, normalized-only shape. These branches are mutually exclusive adoption candidates; do not combine their versioned data formats or interpret prototype schema3/4 rows as this contract.
