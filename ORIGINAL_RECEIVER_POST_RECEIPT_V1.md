# Post-POST receiver receipt v1 candidate

`src/original-receiver-post-receipt-contract.mjs` defines a separate, offline evidence join. It accepts only a genuine in-process `HELD_BEFORE_POST` result from the envelope3 contract. It then checks a canonical receipt against a separately authenticated sender-attempt record and a separately authenticated receiver receipt. Both authenticators are host callbacks; this repository supplies only synthetic test callbacks. The result remains `HOLD`, grants no physical-send authority, and leaves replay disposition unresolved.

The sender attempt binds a fresh attempt ID to the held claim-witness digest, Original request ID/nonce, authenticated sender principal, credential owner/ID/generation, channel binding, and exact method, URL, ordered-header hash, raw body hash and byte count. The receiver receipt binds that attempt ID to deployed recipient identity/build/generation, the held receiver profile hash (including schema, normalizer and runtime), host-verified transport principal/channel/generation, and one CommunityAI `FactoryIngressObservationV2` projection. The receiver signature covers the complete canonical receipt. A receipt is not accepted merely because it repeats hashes supplied by the caller.

The ASGI projection is the one added by CommunityAI `fe41dd5`: `POST`, exact `/v1/chat/completions` route, sorted allowlisted header names/values, raw `Request.body()` byte count and SHA-256, and the Pydantic-normalized body SHA-256. Its digest uses CommunityAI's sorted, compact Python JSON keys. The current real-Flow fixture maps to 299 raw bytes (`b86e125b…`), ten present headers, normalized SHA-256 `ab288a14…`, and observation digest `f74a1280c837ad1511adacc001b5ed8991f6f7b208c030854f2a7e71bf2dd51e`; the latter was checked with both JavaScript and Python's exact digest recipe. CommunityAI permits four more optional routing headers, making fourteen allowlisted names. The v2 observation does **not** report normalized byte length; the held side's 307-byte commitment cannot be independently length-checked from that API alone.

The host pins a versioned proxy policy and generation. This candidate supports exact preservation of POST and raw UTF-8 body, an explicit sender-URL to receiver-route mapping, and only declared removals of sender-projected headers or additions of the four routing headers. The ASGI projection must equal that transform after lowercase-name sorting. Authorization, host, forwarding, cookies, scheme and receiver network origin are outside the ASGI projection; authenticated deployment identity and transport verification must cover that gap. Any body rewrite, method rewrite, undeclared header, or unknown proxy generation requires a new policy/version and fails this one.

CommunityAI `fe41dd5` does not issue a signed post receipt or carry a request-specific sender attempt ID through its host transport extension. An embedding host would need to authenticate the transport and deployment, bind a fresh per-request attempt carrier outside caller headers, preserve the exact v2 ASGI observation, and issue a receipt signed or MACed under a receiver key whose generation FACTORY trusts. FACTORY's eventual final sender gate would need a durable one-attempt witness and verifier for that same attempt ID, wire and channel binding. Neither component exists here. A schema5 journal and one-use replay fence would also be needed before treating this as an operational claim. The ASGI callback currently runs before bearer validation and before the dispatch claim; this receipt proves only the asserted ingress observation under its missing host trust roots, not bearer acceptance, inference, or provider absence.

The older isolated `factory-original-v3-receiver` prototype has incompatible comparison2/witness2 contents. This receipt is designed only for the held contract in this branch and must not be interpreted by schema3/4 rows or the prototype.
