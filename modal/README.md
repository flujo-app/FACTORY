# Factory open-weight inference

These inference definitions are used by the transient factory pilot; current live results and retirement status are recorded in [QUALIFICATION.md](../QUALIFICATION.md). The coordinator journals its exact App, Volume and newly created proxy-token identities before each external operation. Importing `inference.py` defines resources without deploying them. The definition-only import and policy tests require the locally installed Modal SDK but make no cloud calls.

The initial backend is the official Apache-2.0 [Qwen2.5-Coder-7B-Instruct](https://huggingface.co/Qwen/Qwen2.5-Coder-7B-Instruct), pinned to `c03e6d358207e414f1eca0bb1891e29f1db0e242`. It serves `factory-coder` using vLLM 0.21.0 on one L4. Code quality and actual load latency require evaluation; this choice establishes a small coding backend with official vLLM support. The CUDA image tag and transitive Python packages are not a complete immutable dependency lock.

Set `FACTORY_MODAL_APP_NAME`, `FACTORY_MODAL_VOLUME_NAME` and `FACTORY_MODAL_VOLUME_ID` to the persisted run-owned identities, and use an explicit Modal Environment/profile throughout. Do not activate a different global profile. Create a fresh version-2 weights cache as a separate effect with `modal.Volume.objects.create(name, version=2, allow_existing=False, environment_name=environment)`. Noncreating version-2 hydration must match the recorded ID before deploy/download; runtime guards check it before download/engine launch. An existing name is an ownership conflict. Version 2 is beta and suitable here for rebuildable model weights; keep coordinator databases outside it. Name lookup and mount binding are not an atomic provider ABA guarantee. Legacy version-1 cleanup preserves its original request bytes and remains exact-ID-bound. [Modal Volume documentation](https://modal.com/docs/guide/volumes).

Deploy through `inference.app.deploy(environment_name=environment, strategy="recreate", tag=runIdentity)` without `modal.enable_output()`. Retain `app.app_id` privately and resolve `modal.Function.from_name(appName, "serve", environment_name=environment).get_web_url()`. `max_containers=1` applies to this fixed inference Function pool. Deploying a second App or dynamic variant would create another independently bounded pool. The separate CPU prefetch Function is also limited to one container.

Cache the pinned public weights with `modal.Function.from_name(appName, "prefetch", environment_name=environment).remote()`. Its only return fields are state, model and revision. The endpoint loads from the resulting Volume with Hugging Face offline mode; no owner workspace snapshot, API key, MCP attachment or model agent is copied. Failed/unknown prefetch or deployment effects must be reconciled, not automatically retried. Deployment does not invoke this prefetch or provision a warm GPU because minimum/buffer containers are zero.

The CPU prefetch has a 3600-second Function deadline with hard limits of two CPU cores and 2GiB memory. Its local SDK bridge waits for that configured deadline plus the configured 600-second startup/queue margin, currently 4200 seconds. Preparation validates finite integer bounds before paid dispatch. This margin does not guarantee queue completion or cancellation of remote work when a client exits; an interrupted bridge remains unknown and cannot be replayed. The original 900-second attempt reached the Function timeout while fetching files; it did not prove an HTTP, Xet, storage or memory failure. The model revision and download transport are unchanged.

Create a **new proxy token** using `modal.Workspace.from_context().proxy_tokens.create()`. Store `token_id`, `token_secret` and their `token_id + "." + token_secret` bearer value only in the root-protected private run directory; mode0600 alone is insufficient on Windows. The root runner already uses `ensurePrivateDirectory` from flujo-cloud's private-files utility. Do not send the account API token (`ak-/as-`) to FLUJO. The inference endpoint uses `requires_proxy_auth=True`, so Modal rejects unauthenticated access before GPU startup. [Proxy token auth](https://modal.com/docs/guide/webhook-proxy-auth) accepts standard `Authorization: Bearer wk-....ws-...` and covers all URLs. It is Workspace-scoped on Starter, Environment-scoped with RBAC, and is not App/endpoint-scoped. A dedicated factory Workspace can be created [through account settings](https://modal.com/docs/guide/workspaces), with a separate profile and budget, but this code does not create one or change unrelated billing policy.

POST `${endpoint}/v1/chat/completions` with JSON `{ "model": "factory-coder", "messages": [{ "role": "user", "content": "..." }], "max_tokens": 256, "stream": false }`. Responses follow OpenAI Chat Completions `choices[0].message.content`, `finish_reason`, and `usage`; streaming SSE is preserved. Store prompt/response privately. The middleware permits only text chat, authenticated model inventory and health; it denies tools/media, multiple alternatives and unused routes. It bounds body64KiB, output1024 tokens, context4096 tokens, concurrent requests1, and handler120s. Model exceptions are replaced with generic error bodies and engine logs are discarded. Request cancellation does not constitute billing reconciliation.

FLUJO's current `src/backend/services/model/adapters/openaiAdapter.ts:139` uses `model.baseUrl`, `ApiKey`, and `model.name` through the ordinary OpenAI Chat Completions adapter. Create a dedicated model through POST `/api/model` with same-origin `Origin` and `x-flujo-workspace: factory-pilot`: `{ id: ownedModelId, name: "factory-coder", displayName: "Factory Modal Coder", provider: "openai", adapter: "openai", ApiKey: privateProxyBearer, baseUrl: endpoint + "/v1", contextWindow: 4096, maxTokens: 1024, supportsTools: false, inputModalities: ["text"], outputModalities: ["text"] }`. Bind the dedicated minimal start/process/finish Flow's Process node `boundModel` to that ID with no attachments. Current FLUJO owns transient transport retries inside its adapter; direct factory calls must not replay unknown POST outcomes. Initial benchmarks should call the endpoint directly and then verify the Flow path separately.

[Web Function HTTP requests](https://modal.com/docs/guide/webhook-timeouts) can return303 after150s while underlying work continues. A direct factory client must use `redirect: "manual"` or `"error"`, retain a same-origin result URL privately for read-only reconciliation, and never repeat the generation POST on redirect/timeout. Cold starts can exceed that HTTP window. Avoid repeated `/health` or `/v1/models` polling to prove scale-to-zero: HTTP requests keep the pool warm. Use Modal control-plane inventory for idle evidence.

At [published rates checked2026-10-02](https://modal.com/pricing), one L4 plus hard-capped2 physical CPU cores/16GiB memory projects `$1.021392/hour` of active GPU-container time (`$0.170232/10min`). The active Workspace's read-only rate API returned rounded rates L4 `$0.80/hour`, CPU `$0.0473/core-hour`, memory `$0.008/GiB-hour`, totaling `$1.0226/hour` (`$0.170433/10min`). Prefetch/build CPU time, cold starts, the60s retention window, storage and egress are additional. Rates in `config.json` are estimates; `preflight.py` safely reads the active Workspace's actual rates. Each fresh Modal experiment reserves `$30` against the one shared `$100` allowance; Fly reserved `$10`. See the qualification record for current totals. Reservations are not observed spend.

[Modal budgets](https://modal.com/docs/guide/budgets) apply to the Workspace monthly total or Team/Enterprise Environment compute, not individual Apps. Environment budgets omit storage/egress. An unchanged shared Workspace budget does not establish a new factory$30 hard cap. The coordinator must combine its own durable reservation/admission ledger, run-owned App stop, and observed resource-attributed billing; classify delayed/unavailable meter data explicitly. One-container bounds alone do not prevent indefinite repeated usage.

Teardown is separate journaled effects: stop **the recorded App ID** with `modal app stop <app-id> --yes --env <environment> --profile <profile>` (captured output, no log streaming); verify stopped through control-plane inventory; delete **only the recorded Volume** with `modal.Volume.objects.delete(name, allow_missing=False, environment_name=environment)` or `modal volume delete <name> --yes --env <environment> --profile <profile>`; delete **only the newly created recorded proxy token** with `workspace.proxy_tokens.delete(token_id)`. An unknown stop/delete must retain its original identity for reconciliation. Retained weights are a declared retained resource, not complete teardown. Never remove an unrelated token, App or Volume.

Offline checks: `node --test test/modal-config.test.mjs` and `python -B -m unittest test_policy.py` from this directory. No GPU/cloud call/model generation occurs in these tests.

## Coordinated transient pilot

`node scripts/modal-pilot.mjs` prepares read-only: it verifies the original source ownership evidence, reads the dedicated `factory-pilot` configuration, verifies the explicit active Modal profile's actual Workspace and `main` Environment, and checks that deterministic resource names are absent. Its public output contains only selected identities/counts/model metadata. It does not initialize the budget ledger or create run storage.

After review, `node scripts/modal-pilot.mjs --execute` runs deployment, prefetch, direct non-stream generation, a new OpenAI-compatible model and minimal Flow in the existing owned workspace, an actual FLUJO Flow generation, and independent `finally` cleanup. The original Astra model/Flow stay separate. `--through infra|direct|connect|flow` selects the final smoke stage; every choice still retires resources before returning. This runner deliberately offers no persistent retention mode. Successful Flow evidence means the real adapter worked during the smoke; the final active endpoint/model/Flow are retired and removed. A private credential-free fixture template remains available for a new reviewed deployment identity.

The private run directory defaults to `.factory/<run-id>`, and the reservation ID defaults to the same run ID; the unchanged default run ID is `modal-20261002`. Use a fresh `--run-id` for a new attempt and `--reservation-id` for an explicitly selected independent envelope. Resource names are derived from the stable run identity. The Node coordinator applies flujo-cloud's actual `ensurePrivateDirectory` owner-only Windows ACLs before creating SQLite or SDK output. `ModalJournal` persists an immutable operation request digest before every dispatch and uses compare-and-swap state changes. Unknown/running/accepted operations cannot be replayed or bypassed with replacement keys. `run_pilot.py` requires a matching running SQLite intent for each SDK mutation; it removes inherited token/server environment overrides, explicitly selects the recorded profile without changing global activation, and checks actual Workspace identity on every operation. New proxy credentials remain in private checkpoint files.

The common `.factory/spending.sqlite` uses `SpendingLedger`: reserve `modal-20261002` with ceiling3000 cents against the one shared10000-cent budget, then call `start()` before each paid SDK/HTTP dispatch. Fresh work stops at an observed reservation ceiling or global overcommit. Owned retirement keeps the whole ceiling reserved pending final provider billing; the driver does not settle an incomplete meter or call an estimate a charge. Its immediate report selects recorded App/Function/Volume object IDs but cannot finalize partial-hour or image-build charges. The common ledger may therefore continue to show3000 cents committed and final metered spend unknown after confirmed teardown.

Public stage notifications contain allowlisted resource IDs/status/timing/tokens. SDK/CLI diagnostics, HTTP bodies, result URLs, source/profile metadata and all credentials stay private. An unresolved redirect or timeout records an unknown generation and never repeats its POST. A confirmed201 HTTP ownership receipt can support cleanup if a later local fixture checkpoint fails; it does not replay or silently settle the original unknown creation effect. Cleanup disables the owned model first, deletes only the new token, stops only the recorded App ID after live identity verification, requires stopped state plus zero containers, verifies the Volume ID before deletion, and removes only the created Flow/model after content checks. Every teardown is attempted independently; notification failure does not prevent it. Any unknown teardown or fixture removal prevents a complete/retired success claim.

The current direct action can observe a303 result before settling: it validates the exact original HTTPS origin/path and opaque nonempty query, then uses at most three body-free GETs within the original shared600-second deadline. Private per-hop receipts bind the original App/request/effect. An invalid continuation, exhausted deadline or nonterminal result leaves the original generation unknown; its POST is never repeated. This observation path does not establish result availability after token/App retirement.

The minimal Process node sets `maxTokens: 64` directly because the running FLUJO Flow path does not forward HTTP `max_tokens` to that node. Acceptance requires one index-zero assistant choice, a normal stop, no tool/function calls, the expected returned model and exactly the ready object; FLUJO must also report completed. Original uncapped fixtures are retired against their own authored bytes and creation evidence rather than the new template.

Partial billing selects exact recorded App, Function and Volume IDs in the recorded environment and completed UTC hours. It sums each provider row's total once, preserving exact USD and report boundaries privately. Duplicate rows or positive App/Function costs in the same hour make attribution unavailable. Conservative rounded cents can update the ledger; final-hour/build/remaining charges stay unverified, final spend stays unknown and full reservation holds remain.

`node scripts/modal-pilot.mjs --execute --cleanup` observes the original manifest and attempts only previously unadmitted owned cleanup operations. It starts no paid work and never retries an unknown operation. Cleanup attempts get separate immutable reports; original execution/retirement evidence remains unchanged. If provider outcome is unknown, retain original identities and perform read-only reconciliation before further mutation. A refused ordinary rerun also preserves original evidence.

Runner checks: `node --test test/modal-pilot.test.mjs test/modal-config.test.mjs`. The Node cases include fake provider/FLUJO transport and shared-ledger behavior; the Python suites use fake SDK objects for profile isolation, durable intent checks, resource identity mismatches and terminal-state proof. No live deployment occurs in these checks.
