# Distributed CommunityAI host supervisor

`scripts/communityai-modal-supervisor.mjs` and `communityai_modal_driver.py` add the resource lifecycle seam for the fixed four-role mesh: one TLS bootstrap, two distinct GPU block workers (`0:14` and `14:28`), and one text peer. The Node helper reuses `ModalJournal`, `FactoryControl`, and `SpendingLedger`. The Python driver uses Modal Sandbox APIs. Neither module contacts Modal at import, discovers credentials, deploys an App, builds/imports an image, creates a Volume, downloads weights, or sends inference.

This is Source integration. It is not live distributed inference, Fly worker qualification, authenticated Original admission, or billing finality. The current fully held $100 cap and paused Original controller cannot start this path. Worker/text exec and the four-role batch are unconditionally held for the missing reviewed local-only model loading interface. A local image build does not provide that interface, a reviewed registry address, or the owner-verified Modal Image mapping required here.

## Required owner interfaces

The trusted host must supply an existing hydrated deployed App, reviewed registry image by digest and its already built Modal Image ID, a separately verified pinned artifact Volume ID and evidence digest, and an existing bounded paid reservation. The artifacts must contain the manifest's exact Qwen/Qwen3-1.7B revision. The driver mounts them read only at `/models`; offline Hugging Face settings stay enabled. Those settings alone do not prevent the pinned runtime's custom Hub download path. The host must also supply current resource admission in both languages, a protected private run directory, the actual driver bridge, and an existing explicit Modal Client for create and recovery. No operation defaults to `Client.from_env()`. These interfaces have no default or CLI/env authority loader.

The artifact/lock boundary must keep the verified artifact root immutable and give each role a separate owned writable scratch cache for `blocks.lock` and staging, outside the read-only mount. The currently inspected CommunityAI source (`2d08f31aa58c2c7b49304d0367ab51ae9aaccb11`) always opens `cache_dir/blocks.lock` with `wb+`, and its loaders do not propagate the verifier's explicit local-only `artifact_root` through both public worker/text CLIs and every loader. Pointing `cache_dir` at `/models` fails; merely moving it to an empty writable directory can enable fallback downloads. A reviewed upstream interface must bind the read-only verified artifact root explicitly, reject missing/corrupt artifacts without network fallback, propagate it through both role loaders, and keep scratch writes separate. This supervisor does not monkeypatch verifier initialization or issue an unsupported CLI flag. The existing built image does not contain that new seam; new source, image and cache qualification are required before a later commit can replace the hold.

The pinned worker CLI already accepts the complete set of `--expected_manifest_digest`, `--expected_block_indices`, `--expected_artifact_bytes`, `--expected_artifact_set_digest`, and `--expected_cache_root`. Future launch planning must supply all five together, with exact spans `0:14`/`14:28` and a canonical owned writable scratch root. Per-span bytes and artifact-set digests must come from the verified checkpoint index and manifest selection; formation and manifest identity alone cannot derive those claims. No values are invented here, no partial claim set is emitted, and the existing `build_launch_plan` is configuration pending this reviewed boundary.

Signed catalog freshness qualifies automatic production model selection. The currently inspected bundled catalogs are expired and omit this fixed candidate, so they cannot qualify that selection. Direct fixed-manifest CLI experiments can be structurally accepted under explicit trusted owner experiment admission; they still require separate resource, cache, runtime and paid authority. This module does not add a universal signed-catalog requirement to that manual experiment path or grant any admission by itself.

The Node `hostResourceAdmission(request)` and Python `host_admission(request)` are synchronous trusted host functions. They must bind the exact request to the same current controller/management authority, resource ownership, registry-to-Modal image mapping, model-cache verification and paid reservation, and must recheck immediately before every SDK call. Passing a function or digest alone is not proof of this authority. Node checks its exact supplied `FactoryControl` and `SpendingLedger`; starts require an active task management lease, positive unallocated budget, a matching existing Modal reservation and unpaused admission. The helper never resets the cap, reserves new funds, releases funds, or marks billing final.

An owner implementing the Node-to-Python driver bridge must preserve the actual invocation and SDK process handles. An IPC JSON result must not invent or serialize an opaque `ContainerProcess` into a purported reattach ID. Modal 1.5.5 exposes no public durable exec-process reattach API. The required `process` result is the actual owner bridge's live observation handle; the Python driver returns its actual SDK `ContainerProcess` to its in-process caller.

The bounded `resolve_ipv4(tcp_host)` observer must resolve the actual raw tunnel hostname and retain that DNS observation. `observeBootstrap(actual_handle, owned_checkpoint)` must consume the bootstrap child startup record under a host deadline; a timeout leaves that same actual invocation for observation or owned retirement. Never restart it because an observation times out. The startup record is provisional reachability information, not authenticated provider/Original or full-mesh readiness proof.

## Lifecycle and durable recovery

The caller supplies `ModalJournal` at `<runDirectory>/modal.sqlite`. Each role has one `create-role:<role>`, `launch-role:<role>`, and `terminate-role:<role>` operation. A durable running intent with the exact request digest must exist before create, config write, exec, or termination. The Python driver independently reads that same journal in read-only mode and rechecks it and host admission before SDK calls. It also fsyncs one exclusive per-role operation dispatch claim before any SDK access; a running row after a crashed bridge cannot replay the operation, including a create with no returned ID. These local claims are never reset here. Existing accepted/running/unknown/succeeded operations are observation-only in the Node helper; no automatic mutation retry occurs.

Every Python role dispatch holds an exclusive OS lock on `<role>-checkpoint.lock` across its checkpoint reads, SDK observations and replacements. This includes create, launch, observation and retirement. Another invocation of the same role fails immediately with `RoleBusyError` before SDK work; independent roles remain available. The protected lock file persists and the OS releases the lock when its process closes. That release never removes or resets a durable mutation claim. Node reads atomic checkpoints, but Python rechecks the current owned checkpoint and retirement fence under its lock before acting.

The Python driver persists `<role>-resource.private.json` with the exact Sandbox ID before fetching tunnels or performing DNS observation. It retains the actual `Tunnel.tcp_socket` host and random public port separately from the corresponding global IPv4 formation endpoint. Peers carry their native application TLS over `unencrypted_ports=[31330]`; Modal TLS termination and a guessed port 443 are not substitutes. Separately admitted role creations have distinct names/tags. Modal's relative timeout is computed from the host's bounded absolute expiry; it is not evidence of actual provider death at that instant. Only the two worker roles request GPUs. The bootstrap launch writes the fixed endpoint config and uses `communityai_runtime_watchdog.py`; worker/text exec remains held.

Create uncertainty with a checkpoint permits observation and retirement of that exact known Sandbox ID. Create uncertainty without any checkpoint requires an owner/provider inventory join; this module does not infer absence or replay the create. Exec uncertainty is marked before the SDK call and can never replay. On host restart opaque live exec handles are lost; resource observation/retirement remains available, with no claim of a resumed process.

Termination is one durable mutation followed by an actual poll. Its `terminate_requested_unverified` launch fence is persisted before the potentially uncertain SDK call. A pending or failed observation remains unknown and is never repeated as a termination. Launch rejects `terminate_requested_unverified`, `terminate_pending`, or `sandbox_terminal_observed` before config writes, exec or a dispatch claim. A later running poll is returned as that actual observation while preserving the existing retirement fence and any observed terminal exit code; it cannot revive a retired target or erase newer launch state. Retirement of an already terminal owned target revalidates current host admission, exact durable intent and owned identity under the role lock, then returns the retained terminal result without another SDK call or a checkpoint downgrade. `observeRole` can inspect a known Sandbox while admission is paused when the explicit host callback admits that owned read; similarly the explicit owned retirement callback can admit cleanup while starts are paused. A terminal Sandbox poll is retained as a resource observation. It does not authenticate all descendants, close external resources, finalize charges, or settle the paid reservation. The reused journal's generic settlement drops Sandbox-specific fields; private checkpoints are mandatory and retain those facts instead.

## Owner invocation

Construct `createCommunityAiModalSupervisor` with the exact supplied authorities, journal, private-file helper, driver bridge, explicit resource admission and complete resource `spec`. `launchFourRoles` currently refuses with `COMMUNITYAI_MODEL_RUNTIME_UNQUALIFIED` before any gate, paid state change, journal intent, driver call or resource creation. Worker/text `launchRole` also refuses before private record/driver work. These holds have no caller override. Explicitly admitted standalone `createRole`, bootstrap `launchRole`, known-resource `observeRole` and `retireRole` remain available, always with `NO_ADMISSION` and no inference qualification. The host owns failure cleanup and must keep the same live invocation until closed; use `retireRole(role)` for every known owned target and `observeRole(role)` for uncertain retirement. Configured provider lifetime bounds remain in place if the host fails.

The coordinator remains an explicit owner-host composition: Python `create_owned_coordinator(formation, host_admission=..., factory_admission=..., api_key_identifier=...)` delegates to the existing `create_coordinator_app`. It requires real current Original admission and credential adapters. A deployable remote coordinator carrier, actual request-specific Original/sender/receiver trust join, durable schema5 replay fencing, applicable production catalog freshness, API TLS/proxy binding, end-to-end inference checks and model coverage observations remain required owner integration. No default-admit callback, synthetic receiver receipt or alternate monolithic model route is added.

## Offline checks

Run `python -B -m unittest -v test_communityai_modal_driver.py` in `modal/` and `node --test test/communityai-modal-supervisor.test.mjs` from the repository with its existing dependencies available. Checks use only fresh owned SQLite journals and SDK/driver doubles. They cover exact running intent and owner refusal, distinct role sockets/two GPU creation requests/read-only artifact mounts, fixed bootstrap execution, retained IDs after tunnel failure, lost create/exec/terminate acknowledgments, no replay after restart, paused/free-zero starts, owned cleanup while starts are paused, foreign checkpoint refusal and non-final spending. Controlled OS-lock interleavings check observation during exec and launch during termination; retirement markers remain fenced after later running observations. The batch/model hold checks zero driver/SDK starts. Checks do not execute a provider, load a model, exercise actual Modal transport, or qualify the owner bridge.

SDK contracts were inspected in local Modal 1.5.5 source and the official [Sandbox reference](https://modal.com/docs/sdk/py/latest/Sandbox), [Volume mount reference](https://modal.com/docs/sdk/py/latest/Volume), and [raw TCP tunnel guide](https://modal.com/docs/guide/tunnels).
